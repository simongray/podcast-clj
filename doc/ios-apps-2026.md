# iOS apps, October 2026

This report looks at the ways an iOS app could use podcast-clj, written on
9 October 2026. It's frozen as of that date and won't be updated. Facts
about other software come from its documentation, code, releases or
issues, with a few forum logs marked as such. Nothing was tested on an
iPhone; the parse times were measured on an Apple M1.

The quickest way to put podcast-clj in an iOS app today is the ClojureScript branch it already has, run in a web view or in React Native, with Swift for the player, background downloads and CarPlay. The report answers four questions:

1. **Can GraalVM compile the library into a native library for a Swift or Objective-C app?** Yes: Native Image can compile the JVM branch into a static library that a Swift app calls through C entry points, and the grease project does it with Clojure 1.12 in 2026. But Oracle doesn't support iOS, Gluon's last final iOS-capable GraalVM is from 2022, and no Clojure app has reached the App Store this way.
2. **What about React Native?** React Native with Expo runs the ClojureScript branch once you add an XML parser, WebCrypto, a full `TextDecoder` and two stores. Native `fetch` removes the CORS proxy, but Hermes has no JIT on iOS and CarPlay support is weak.
3. **What about a web view for most of the UI?** A web view runs the library almost as Safari does, JIT included. You add a `:send` over native HTTP and a store iOS won't evict, and you keep playback native, because iOS suspends the web view in the background.
4. **Is there a Clojure state of the art?** For native apps it's ClojureDart, which has apps in the App Store but would need a third `:cljd` branch through the library and its three dependencies. For ClojureScript it's shadow-cljs's `:react-native` target with Expo, whose largest user, Status, was archived in July 2026.

On every path, background audio, downloads and CarPlay are native code you write or a plugin you pick. That matches how the library is built: it plans, and the app plays, downloads and draws. The recommendation at the end is Capacitor first, with Expo as the fallback if Clojure code must run while the phone is locked.

## GraalVM builds an iOS library, on a toolchain nobody supports

Native Image can emit a relocatable object for `IOS_AARCH64`, which you archive into a `.a` and link into an Xcode project. The grease project does exactly this: it builds Clojure 1.12.4 with Oracle GraalVM 21.0.3, `-Dsvm.platform=…IOS_AARCH64` and a static JDK 21 built from phronmophobic/ios-graal-jdk-21, then links the object into an Xcode app ([grease compile-shared](https://github.com/phronmophobic/grease/blob/main/scripts/compile-shared)). A Swift app calls such a library through `@CEntryPoint` functions and the generated headers. **Only primitives and pointers cross the boundary**, so strings travel as `char*`, and calls back into Swift are C function pointers invoked through `@InvokeCFunctionPointer` ([GraalVM: native shared library](https://www.graalvm.org/latest/reference-manual/native-image/guides/build-native-shared-library/)). Any thread other than the one that created the isolate must call `graal_attach_thread` first ([GraalVM C API](https://www.graalvm.org/latest/reference-manual/native-image/native-code-interoperability/C-API/)). The Clojure rules are the familiar ones: initialise Clojure classes at build time with graal-build-time, remove reflection, and don't `eval` at run time, which the library already avoids ([clj-easy/graal-docs](https://github.com/clj-easy/graal-docs)). No public example has Swift, rather than C or Objective-C++, calling such a library.

The trouble is the toolchain. On 2024-04-16 an Oracle maintainer wrote that **"we don't support iOS platform and we currently do not have any plans to support it"** ([oracle/graal#8776](https://github.com/oracle/graal/issues/8776)). Gluon's fork, the only packaged route, made its last final release, gluon-22.1.0.1-Final (Java 17), on 2022-06-08. Its last build is a JDK 23 dev build of 2024-09-08, and GluonFX 1.0.26 rolled back the plugin changes that used it as experimental ([gluonhq/graal releases](https://github.com/gluonhq/graal/releases); [Gluon docs](https://docs.gluonhq.com/)). Everyone else builds a static JDK, and those builds rot. In January 2026 a developer rebuilding grease on a community JDK 21 got undefined symbols for socket and EC crypto natives, and phronmophobic replied that "there's been a lot of bitrot" ([#graalvm-mobile, 2026-01-26](https://clojurians-log.clojureverse.org/graalvm-mobile/2026-01-26), a forum log). Gluon has had an open bug since 2023 where `URL.openStream()` fails on IPv6 networks on iPhones ([substrate#1224](https://github.com/gluonhq/substrate/issues/1224)), and App Review tests apps on an IPv6-only network ([Apple forums, 2016](https://developer.apple.com/forums/thread/49979)). This research found **no Clojure app in the App Store built this way**. The grease project reached a public TestFlight beta as mobiletest in 2021–22 and runs user code through SCI rather than compiling it ([mobiletest](https://github.com/phronmophobic/mobiletest)). Its last commit is from 2026-06-28, and in July 2026 neither phronmophobic nor frankitox, who ported it to Android, planned to maintain their projects ([#graalvm-mobile, 2026-07-30](https://clojurians-log.clojureverse.org/graalvm-mobile/2026-07-30)).

If you try it anyway, the library needs adapters but no new branch:

| Part | What you'd build |
|---|---|
| API | A few entry points that take and return EDN or JSON strings, e.g. `pc_init`, `pc_call` and `pc_free`, with the app's atom inside the isolate. The grease project generates its entry points with dtype-next ([grease.clj](https://github.com/phronmophobic/grease/blob/main/src/com/phronemophobic/grease.clj)). |
| HTTP | A `:send` that calls a Swift function pointer over URLSession and waits for the completion handler. |
| Nostr | A relay `:send` over `URLSessionWebSocketTask`. Comments and Nostr Wallet Connect already accept one in place of `nostr/send!`. |
| Stores | Nothing new. The file store takes a path, and Swift passes one in the app container. |
| Packaging | An XCFramework with device and simulator slices, which no public example shows. |

Route all HTTP through Swift even if the JDK client works, since that keeps TLS, DNS and IPv6 out of the static JDK. Expect to link the JDK's networking natives anyway, though: the JDK client stays in the image as the default `:send`, and its natives are the kind that failed to link in January. The native side is the strong part of this path. The app is an ordinary Swift app with AVPlayer, Now Playing, a background URLSession, BGTaskScheduler and CarPlay templates, and no plugin layer in between. Ahead-of-time compiled code is fine for App Review, but an SCI REPL that runs downloaded code breaks guideline 2.5.2, so keep it to debug builds ([App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). No one has published the size, start-up time or memory of a Clojure native image on an iPhone; a spike should measure those first.

The older JVM routes don't help. MobiVM is maintained (2.3.26 on 2026-08-11), but nobody has reported running Clojure on it since about 2015 ([MobiVM changelog](https://github.com/MobiVM/robovm/wiki/Changelog)). Codename One forbids the reflection Clojure's runtime needs ([Codename One](https://www.codenameone.com/blog/how-to-port-jvm-languages-to-codename-one/)), and clojure-objc was last pushed in 2015 ([clojure-objc](https://github.com/galdolber/clojure-objc)).

## React Native runs the ClojureScript branch after five additions

React Native 0.87.1 is current. It has run only on the New Architecture since 0.82 and has used Hermes V1 by default since 0.84 ([RN 0.84](https://reactnative.dev/blog/2026/02/11/react-native-0.84)). **Hermes V1 has no JIT and no ahead-of-time native compilation in React Native yet** ([RN 0.82](https://reactnative.dev/blog/2025/10/08/react-native-0.82)), and iOS gives apps no writable executable memory ([RN docs](https://reactnative.dev/docs/javascript-environment)), so JavaScript runs interpreted. Expo SDK 57 (RN 0.86) is current, and SDK 58 (RN 0.88) has been in beta since 2026-09-15 ([Expo SDK 57](https://expo.dev/changelog/sdk-57); [SDK 58 beta](https://expo.dev/changelog/sdk-58-beta)). The shadow-cljs `:react-native` target works with Expo, with hot reload and a REPL into the running app ([shadow-cljs guide](https://shadow-cljs.github.io/docs/UsersGuide.html#target-react-native)). The library is then one more set of namespaces in that build.

Here is where each API the ClojureScript branch uses comes from in the three JavaScript hosts on iOS:

| API the branch uses | WKWebView (Capacitor) | Hermes (Expo SDK 57) | Bare `JSContext` |
|---|---|---|---|
| `fetch` with streamed bodies | Yes, but CORS applies | Yes (`expo/fetch`), no CORS | No |
| `WebSocket` | Yes | Yes | No |
| `DOMParser` | Yes, native | No: `@xmldom/xmldom` | No |
| `crypto.subtle`, `getRandomValues` | Yes, in a secure context | No: react-native-quick-crypto | No |
| `TextDecoder` for latin1 and UTF-16 | Yes | No: UTF-8 only | No |
| `AbortSignal.timeout` | iOS 16+ | RN 0.87+ (SDK 58) | No |
| `indexedDB` | Yes, but evictable | No | No |
| File System Access, for the file store | OPFS only; `createWritable` from iOS 26 | No | No |
| `BigInt`, `Uint8Array`, `Promise` | Yes | Yes | Yes |
| JIT | Yes | No | No |

Sources: [MDN browser-compat-data 8.1.5](https://www.npmjs.com/package/@mdn/browser-compat-data) (its WKWebView column mostly mirrors Safari), [React Native's setUpXHR.js](https://github.com/react/react-native/blob/main/packages/react-native/Libraries/Core/setUpXHR.js), [Expo's built-ins](https://docs.expo.dev/versions/latest/sdk/expo/), and a `typeof` check of a bare `JSContext` on macOS made for this research.

On Expo, that means five additions. Install `@xmldom/xmldom` as `globalThis.DOMParser`, as in Node. Call react-native-quick-crypto's `install()`, which covers PBKDF2, AES-GCM, SHA-256 and `getRandomValues` ([coverage table](https://github.com/margelo/react-native-quick-crypto/blob/main/.docs/implementation-coverage.md)). Add a complete `TextDecoder`: Expo's handles only UTF-8 ([Expo docs](https://docs.expo.dev/versions/latest/sdk/expo/)), while `util.xml` asks for latin1 to read the XML declaration and then for whatever encoding a feed declares. At best, non-UTF-8 feeds decode wrongly; if Expo's decoder throws on other labels, so does every feed whose Content-Type names no charset. Shim `AbortSignal.timeout` until SDK 58, since React Native got its own `AbortSignal` with `timeout` only in 0.87 ([RN 0.87 source](https://unpkg.com/react-native@0.87.0/src/private/webapis/dom/abort-api/AbortSignal.js)). Write two stores: a key-value one over expo-sqlite or MMKV in place of IndexedDB, and a folder one over expo-file-system's `Paths.document`, which iOS doesn't purge ([Expo FileSystem](https://docs.expo.dev/versions/latest/sdk/filesystem/)). Keep Expo's streaming `fetch` as the global one, since the library reads bodies through `res.body.getReader()`. Native networking has **no CORS** ([RN networking](https://reactnative.dev/docs/network)), so `util.proxy` goes away, though plain-http feeds need an App Transport Security exception.

Interpreted JavaScript is the cost. JavaScriptCore without its JIT ran a web tooling benchmark about 7.5 times slower ([Coote, 2020](https://dev.to/alastaircoote/to-jsc-or-not-to-jsc-running-javascript-on-ios-in-2020-44ba)). Measured for this research on an M1 core, xmldom parsed the 6.2 MB changelog.xml corpus feed in about 0.1 s with a JIT and **0.55–0.8 s without one**, before the library walks the DOM. Feeds under 1 MB stay well under 200 ms. A refresh of several large feeds will still stall the JavaScript thread, so run it in the background task and let conditional requests skip unchanged feeds.

Expo covers most of the platform. The expo-audio package gives background playback, lock-screen controls, playlists and rates up to 2.0 ([Expo Audio](https://docs.expo.dev/versions/latest/sdk/audio/)). Background downloads run on a background URLSession through expo-file-system, whose JavaScript task isn't restored after iOS terminates the app, or through kesha-antonov's downloader, which re-attaches ([Expo FileSystem](https://docs.expo.dev/versions/latest/sdk/filesystem/); [react-native-background-downloader](https://github.com/kesha-antonov/react-native-background-downloader)). BGTaskScheduler work is defined in JavaScript with expo-background-task ([Expo BackgroundTask](https://docs.expo.dev/versions/latest/sdk/background-task/)). **CarPlay is the gap.** The react-native-carplay README says "No Expo support due to Scenes", and its last npm release is from June 2024. The one player that advertises CarPlay, react-native-track-player V5, is commercially licensed ([react-native-carplay](https://github.com/birkir/react-native-carplay); [react-native-track-player](https://github.com/doublesymmetry/react-native-track-player)). Plan on writing an Expo module in Swift for CarPlay. Podverse, the nearest open-source precedent, shows the cost: it stayed on RN 0.66 with a forked player and a stale CarPlay library, and its repository has been quiet since April 2025 ([podverse-rn](https://github.com/podverse/podverse-rn)).

A Swift app can also run the same build in JavaScriptCore without React Native. A bare `JSContext` has the language and little else, so you'd write timers, the `:send` over URLSession, a WebSocket, a CryptoKit-backed `crypto.subtle`, stores and a `TextDecoder` in Swift. One developer put such a runtime at about 1,000 lines of Swift ([Cocoanetics, 2026](https://www.cocoanetics.com/2026/05/look-what-javascriptcore-has-been-doing-in-my-pocket/)). It has no JIT, but it runs in the app's process, so it keeps running while the app plays audio or runs a background task. That suits a SwiftUI app with its podcast logic in ClojureScript, at the price of a runtime you build and maintain yourself, with no prior art for ClojureScript.

## A web view runs the library nearly as Safari does

Capacitor serves the app from `capacitor://localhost` ([Capacitor config](https://capacitorjs.com/docs/config)), and WebKit treats a scheme handled by a scheme handler, a localhost host and local schemes as potentially trustworthy ([SecurityOrigin.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/SecurityOrigin.cpp)). **The page is a secure context, so `crypto.subtle` works**, and every other API the branch uses is there too (table above). WKWebView runs JavaScript in a separate process with a JIT, which a WebKit engineer gave Lucid as the reason to prefer it over JavaScriptCore on iOS ([Lucid, 2019](https://lucid.co/techblog/2019/01/03/javascriptcore-10-months-later)). Two limits apply. There's no `showDirectoryPicker`, and `createWritable`, which the file store uses, arrived only in iOS 26, so a file store over OPFS needs iOS 26. The library's use of `AbortSignal.timeout` sets an iOS 16 floor.

CORS comes back, because WebKit registers every scheme-handler scheme as CORS-enabled ([WebPage.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/WebProcess/WebPage/WebPage.cpp)). CapacitorHttp sends requests through native code: you can switch on its patching of `fetch` and `XMLHttpRequest`, or call `CapacitorHttp.request` directly ([CapacitorHttp](https://capacitorjs.com/docs/apis/http)). A `:send` over `CapacitorHttp.request` is the cleaner choice. It sends only the library's traffic natively, and the docs don't say whether the patched `fetch` honours `AbortSignal` or streams bodies. Enclosures shouldn't cross the bridge at all, since the same page warns about large transfers and points to file-transfer plugins.

IndexedDB persists to disk in the default data store ([WKWebsiteDataStore](https://developer.apple.com/documentation/webkit/wkwebsitedatastore)), but Capacitor's own guide says **iOS can reclaim a web view's IndexedDB** when space runs low ([Capacitor storage](https://capacitorjs.com/docs/guides/storage)). WebKit bug 277615 lost IndexedDB connections in a Capacitor app after background memory pressure on iOS 17.6 to 18.4. The fix landed in WebKit in March 2026, with no shipping iOS version stated ([WebKit bug 277615](https://bugs.webkit.org/show_bug.cgi?id=277615)). Keep the profile in a store of your own over SQLite or files, and treat IndexedDB as a cache.

Playback has to be native. HTML audio keeps playing a started track in the background, but iOS suspends the web view soon after the app leaves the foreground, so Media Session lock-screen buttons stop responding ([Capawesome, 2026](https://capawesome.io/blog/how-to-play-audio-in-the-background-in-capacitor/)). Starting the next track from JavaScript while locked failed in a 2024 report on iOS 17.2.1 ([Apple forums](https://developer.apple.com/forums/thread/713084)). A native player plugin must own the queue, Now Playing and the remote commands, and report positions when the web view wakes. The free option is @capgo/capacitor-native-audio, and Capawesome's Audio Player is paid ([npm](https://www.npmjs.com/package/@capgo/capacitor-native-audio); [Capawesome Audio Player](https://capawesome.io/docs/sdks/capacitor/audio-player/)). For background downloads, @capgo/capacitor-downloader uses a background URLSession ([capacitor-downloader](https://github.com/Cap-go/capacitor-downloader)). **Background refresh is the weak spot.** Capacitor's Background Runner is a separate JavaScript context with no DOM, a fresh context per run and about 30 seconds of time ([Background Runner](https://capacitorjs.com/docs/apis/background-runner)), so the library would need xmldom and a key-value store there. Whether a BGTask can instead wake the web view long enough for a refresh is undocumented. For CarPlay, @capgo/capacitor-auto (since May 2026) pushes list templates and doesn't mention Now Playing ([capacitor-auto](https://capgo.app/plugins/capacitor-auto/)), so expect to write a Swift plugin.

Capacitor itself is healthy: 8.5.3 shipped on 2026-10-07 and 9.0 is in alpha ([npm @capacitor/core](https://www.npmjs.com/package/@capacitor/core)). Ionic stopped selling its commercial products in 2025 but says it will keep maintaining Capacitor ([Ionic blog](https://ionic.io/blog/?p=6282)). A shadow-cljs `:browser` build writes into Capacitor's `webDir`, and during development `server.url` can point at the shadow-cljs dev server, which Capacitor's docs say not to ship ([Capacitor config](https://capacitorjs.com/docs/config)). The UI is HTML, so Replicant works as it does in a browser. A bundled app that works offline, with a native player and CarPlay, is well clear of guideline 4.2's "repackaged website" rejection ([App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). No ClojureScript app shipped with Capacitor turned up, only tutorials from around 2022.

The other web-view paths are weaker. A hand-made WKWebView shell works the same way, but you write the scheme handler, the HTTP bridge and every plugin in Swift. Tauri 2 has supported iOS since 2024-10-02, but it adds a Rust layer the library doesn't need, has no audio or download plugins, and Tauri 3 has been in alpha since 2026-09-13 ([Tauri 2.0](https://v2.tauri.app/blog/tauri-20/); [npm @tauri-apps/cli](https://www.npmjs.com/package/@tauri-apps/cli)). Hotwire Native wraps server-rendered pages and has no offline story ([Hotwire Native](https://native.hotwired.dev/overview/how-it-works)). An installed PWA keeps the CORS proxy, gets no background downloads, refresh or CarPlay, and its standalone audio failed again in reports on iOS 26.0.1 ([Apple forums](https://developer.apple.com/forums/thread/805900)).

## ClojureDart leads native Clojure, and Expo leads ClojureScript

| Project | Approach | Status on 2026-10-09 | On iOS |
|---|---|---|---|
| [ClojureDart](https://github.com/Tensegritics/ClojureDart) | Clojure compiled to Dart, then AOT by Flutter | 0.9.20261002 tagged; REPL in beta | Roam Research and Paddle Express in the App Store |
| [shadow-cljs](https://shadow-cljs.github.io/docs/UsersGuide.html#target-react-native) with Expo and [UIx](https://cljdoc.org/d/com.pitch/uix.core/1.4.6/doc/using-react-native-with-uix) | ClojureScript on React Native | shadow-cljs 3.5.5 (2026-10-04); UIx has an Expo template | Status, now archived |
| [grease](https://github.com/phronmophobic/grease) | Clojure in a native image, user code in SCI | Last commit 2026-06-28; experimental; GPLv2 | TestFlight beta in 2021–22 |
| [jank](https://book.jank-lang.org/print.html) | Clojure on LLVM | Alpha since January 2026 | No iOS target |
| [ClojureCLR](https://github.com/clojure/clojure-clr) | Clojure on .NET | Active | No reports; NativeAOT ruled out |
| Krell, re-natal, clojure-objc, lein-fruit | Older routes | Last pushed 2024, 2019, 2015 and about 2014 | Stale or dead |

**ClojureDart is the only Clojure dialect with native iOS apps in production.** Its README thanks Roam Research for building its App Store and Play Store apps on it, and Paddle Express shipped in 2023 ([ClojureDart README](https://github.com/Tensegritics/ClojureDart); [Paddle Express](https://clojurians-log.clojureverse.org/announcements/2023-09-13)). Porting the library means a third host branch, not a recompile. The ClojureDart reader always has the `:clj` feature on, so `:clj` must come last in every conditional, or the JVM branch is silently read ([ClojureDart FAQ](https://github.com/Tensegritics/ClojureDart/blob/main/doc/FAQ.md)). At commit 946cd6d the library has about 250 reader conditionals in 53 of its 75 `.cljc` files, and html-pieces, drop-in-search and mind-meld need the same work. The Dart side is covered: package:xml for event parsing, package:cryptography for AES-GCM and PBKDF2 through CryptoKit, and dart:io for HTTP, WebSocket and files ([xml](https://pub.dev/packages/xml); [cryptography](https://pub.dev/packages/cryptography)). The async code would follow the ClojureScript branch's promise shape, since Dart has no blocking threads. The Flutter plugins are good: audio_service with just_audio for background playback and the lock screen, background_downloader on URLSession, and flutter_carplay with the shared Now Playing template ([audio_service](https://pub.dev/packages/audio_service); [background_downloader](https://pub.dev/packages/background_downloader); [flutter_carplay](https://pub.dev/packages/flutter_carplay)). Widgets, App Intents and Watch apps would still be Swift. The main risk is a two-person project with a beta REPL.

For ClojureScript, the maintained path is shadow-cljs's `:react-native` target in an Expo development build, with UIx or Reagent 2.0. The community is small. **Status, the flagship ClojureScript app on React Native, was archived on 2026-07-22** in favour of a Nim and Qt app, after never moving past RN 0.73 and the old architecture ([status-legacy](https://github.com/status-im/status-mobile); [Status blog](https://our.status.im/migrate-from-status-legacy-to-unified-status-mobile-app/)). Krell was last pushed in June 2024, and PEZ's Expo template is looking for maintainers ([Krell](https://github.com/vouch-opensource/krell); [rn-rf-shadow](https://github.com/PEZ/rn-rf-shadow)). Static Hermes can compile a ClojureScript app to a native binary, but only on desktop so far, and one demo ran about six times slower than Node ([Liutikov, 2025](https://dev.to/romanliutikov/native-apps-with-clojurescript-react-and-static-hermes-1ebg)). The static runtime of jank is "very similar to a Graal native image", but jank has no iOS target, and ClojureCLR can't use .NET's NativeAOT because Clojure emits code at run time ([jank book](https://book.jank-lang.org/print.html); [#clr, 2025-06-11](https://clojurians-log.clojureverse.org/clr/2025-06-11)).

## Capacitor asks the least of the library

| Path | Work in podcast-clj | Native code still needed | Main risk |
|---|---|---|---|
| Capacitor | A `:send` over CapacitorHttp; a profile store over SQLite or files | Player plugin, downloader plugin, CarPlay plugin (likely your own), refresh outside the web view | Web view suspended in the background; IndexedDB eviction; small plugin vendors |
| Expo | xmldom, quick-crypto, a full `TextDecoder`, an `AbortSignal` shim on SDK 57; key-value and folder stores | A CarPlay module in Swift; Expo covers the rest | Interpreted JavaScript; small ClojureScript community; an SDK upgrade every few months |
| `JSContext` in a Swift app | The Expo list, written in Swift: timers, crypto, WebSocket, `TextDecoder`, a `:send` and stores | Everything, in Swift | No JIT; no prior art |
| Native image in a Swift app | C entry points; Swift `:send`s for HTTP and relays | Everything, in Swift | Unsupported toolchain; static JDKs rot |
| ClojureDart | `:cljd` branches in the library and three dependencies | Flutter plugins; widgets and intents in Swift | Size of the port; two-person project |
| Tauri 2 | A `:send` over the http plugin | Every plugin, in Swift, plus Rust | Thin iOS ecosystem; Tauri 3 coming |
| PWA | None; the proxy stays | Not possible | No downloads, refresh or CarPlay |

Start with Capacitor. It's the only path where the library runs on a JIT with the web APIs it was written for, and the UI can be the Replicant code you'd write for a browser. The library work is a `:send` over CapacitorHttp and a store for the profile. The Swift work is what any podcast app needs: a player that owns the queue and Now Playing, background downloads and a CarPlay scene. A one-day spike settles the open questions: `isSecureContext` on a device, the corpus feeds through the new `:send`, parse time for the largest feeds, a native audio plugin, a background download, and whether a BGTask can run a refresh in the web view. If that last answer is no, and a refresh must run Clojure code while the phone is locked, switch to Expo, whose JavaScript runs in the app's own process. Keep the native image as an experiment until GraalVM ships static JDKs for iOS. Keep ClojureDart for the day you want a Flutter UI and can afford a third branch.

## Conclusion

The library is already shaped for iOS. HTTP, relays and stores are pluggable, and the app owns playback, so every path costs adapters rather than a redesign. Even Nostr, the one protocol outside the HTTP `:send`, takes a relay `:send` in comments and Nostr Wallet Connect, so a native build needs no JDK WebSocket. The real choice is where code runs while the phone is locked. A web view handles the foreground well and leaves the background to Swift. Hermes, JavaScriptCore, a native image and Dart all run in the app's own process and can keep running the library in the background, each at its own price. Decide how much of auto-download, play-position saving and sync must happen with the screen off before you pick the host.

Two things would change this picture: official static JDKs for iOS from GraalVM, which phronmophobic is hoping for, and an iOS target for jank, whose static runtime is the right shape. Neither has been announced.
